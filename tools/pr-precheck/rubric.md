# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff inside the plan | Every file and every hunk in the Candidate PR's diff, read against the Plan context's scope statement, its "Files:" line, its not-in-scope line, and any deviation note the plan records | Every file the diff touches is named by the plan's scope or "Files:" line, or is covered by a deviation note the plan records, and every hunk implements a step the plan states or is covered by such a note. A hunk that adds something the plan did not ask for fails even when the planned fix is also present and correct: a new option, setting, or flag; a rewrite, simplification, or renaming of code the plan does not name; an edit to a file the plan never mentions; or anything the plan's not-in-scope line excludes. Two things count as inside the plan without being named: a test that exercises the planned change, and a changelog, whatsnew, or release-notes entry that the Repo facts' "pull requests:" line asks for. A deviation note counts only when it is recorded in the plan or stated in the description as recorded in the plan; a change explained only by a commit message or a code comment has no note | required |
| Plan delivered or shortfall recorded | Each deliverable the Plan context names (the code change, each named test, a docs or changelog item, each entry on its "Files:" line), read against the diff and against any deferral or deviation note in the plan or the description | Each deliverable the plan names is present in the diff, or its absence is stated as a deferral or deviation in the plan or in the description. A named test, docs update, changelog item, or file that the diff lacks and nothing records as deferred fails. A PR that delivers a stated subset of the plan and says so passes; a limit the plan itself declared ("not covered by this change", "deferred with a note", "a maintainer decision left open") is not a shortfall | required |
| Description matches the diff | Every claim in the Candidate PR's title and description about what the PR changes, adds, covers, or leaves alone, read against the diff's files and hunks | The description names no file, flag, option, behavior change, test, docs change, or changelog entry that the diff does not contain, and makes no fidelity claim ("implements the plan exactly", "no changes beyond the plan", "no functional changes outside X", "exactly as planned") over a diff that failed either check above. A terse description whose every claim the diff supports passes. A claim about what a test covers is read against the test's assertions, not against how many test functions or commits carry it | required |
| Decisive test evidence | The Candidate PR's test-evidence section and any evidence quoted in its description, read against the Plan context's test plan: the repro step it maps to the reported behavior, the expected-after value it states, and the suite or check commands it names | Both of these are shown. (1) The repro the plan's test plan maps to the reported behavior is re-run on the branch with the before state and the after state both stated as observed values (an output line, an exit code, a transcript, a described screen or UI state at the named step; a before line and an after line written as comments in one block count), and the after state is the expected-after the plan stated. Where the issue reports more than one failure mode and the plan's test plan names each by number, each is re-run this way. (2) Every suite, build, or check command the plan's test plan names is reported with its outcome. Evidence that runs only a control, only a path the fix does not change, or a different input from the one the test plan names; a prose assurance with no observable ("tested locally, works now", "verified on my machine for a day"); or a named suite whose outcome is never reported, fails. Secondary test-plan steps (controls, extra observables) may be stated as outcomes without a transcript once (1) is shown | required |
| Reviewable diff | The diff's hunks, read one at a time, and the commit list as context | The diff contains none of: a commented-out line of code (an old attempt, a disabled debug call, an experiment kept "for reference"); a debug print or log left in (`print`, `eprintln!`, `console.log`, `dbg!`, a line or commit tagged `DEBUG`); a function, helper, constant, or import that nothing in the diff uses, including one kept alive with `allow(dead_code)`, `noqa`, or an underscore prefix (an added import that an added line uses is used); a TODO or FIXME added on a line the fix does not otherwise change; or a hunk whose removed and added lines, taken together, change no token (whitespace, line breaks, indentation, ordering, or grouping only; an import or use block rewritten when one added line would have carried the new name counts, and so does a block of lines removed and re-added identically). Any one of these fails. Lines re-printed inside a hunk that does change a token are ordinary diff output, not churn. A comment that explains the fix, a commit message of any quality, and the number of commits never fail this check on their own | required |
| Repo asks and AI disclosure | The Repo facts' "pull requests:" line (template sections, checklist items, required entries such as a closes line, a changelog or whatsnew entry) and its "contribution policy" line, read against the Candidate PR's description and diff | Every section or checklist item the template names appears in the description with content specific to this PR, or is marked not applicable with a reason; every required entry appears where the template puts it (a closes or fixes line in the description; a changelog, whatsnew, or release-notes file in the diff). If the stated policy REQUIRES disclosing AI assistance ("must be disclosed", "all AI usage must be stated"), the description states that AI assistance was used and to what extent; a policy that is silent on AI, welcomes it with a human in the loop, or asks only for the contributor's own words does not require disclosure, and the check passes on that point whatever the description says. Where there is no template and no required entry, that part passes. Asks whose satisfaction is not visible in a PR package (a signed CLA, a vouch flow, CI status, a maintainer discussion before the PR) are not graded. Course packages are treated as AI-assisted work | required |
| Maintainer direction engaged | The Thread highlights' comments by an OWNER, MEMBER, or COLLABORATOR, or by the issue's author, that give direction (a culprit or file, a chosen or rejected approach, a constraint, a test build, an open question put to the fixer), read against the description and the plan | Where such direction exists, the description or the plan names it and follows it or says why it departs. Where the thread has no such direction, this check passes. This check never changes the verdict; it marks a PR a maintainer will recognise as having read the thread | preferred |

## Verdict rule

Accept (ready to submit) only if every `required` check passes. A single
`required` check graded `fail` or `unclear` rejects the package. `unclear`
is treated as `fail`: a PR whose diff, deliverables, evidence, or template
compliance I cannot verify from the package is a PR that is not ready to
submit. The `preferred` check never changes the verdict; it only marks a
stronger PR.

The deciding check is the first `required` check, in table order, that did
not pass; its evidence line is what the summary quotes as the reason for
the hold. When every required check passes, the summary quotes the
before-and-after observable from the test evidence as the thing a reviewer
can hold the PR to.

Eval mode grades the complete package with every check. Live mode grades
the student's own `plan.md` (its Deviations section read as part of the
plan), the branch's diff, the draft title and description, and the
captured test evidence the same way, and grades them again after every
fix before the PR is opened.
